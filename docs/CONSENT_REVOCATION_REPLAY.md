# Consent revocation replay boundary

Jobs identifies a revocation by event ID. A retry must match the saved owner, purpose, policy version, source or decision receipt, correlation ID, revocation time, consumer, status, and integrity hash. Jobs also requires the corresponding consent block to remain active and bound to that event. A conflicting or no-longer-verifiable replay receives `409 revocation-event-conflict` before derivative cleanup is invoked.

An exact retry still repeats cleanup after a transient failure. Older receipts did not store `revokedAt`; those retries are accepted only when the still-current active block supplies the original matching time and event binding. If that block is missing, inactive, or belongs to a later event, the replay fails closed and needs reconciliation. A conflict is not an acknowledgement that another user's consent has been revoked.

With a Firebase CLI and the locked workspace dependencies, run the synthetic transaction tests using `firebase emulators:exec --project demo-urai-jobs-consent --only firestore 'node --test tests/emulator/consent-revocation-replay.test.mjs'`. The actual handler uses a local Firestore emulator; HTTP authentication and derivative cleanup are mocked. The test does not prove delivery from Privacy or cleanup against hosted Storage.

The endpoint accepts the legacy `consent.revoked.v1` decision-receipt shape and the `consent.revoked.v2` source-receipt shape prepared by Privacy. The two receipt types remain distinct and event versions cannot be mixed during a replay. The local cross-service emulator test exercises projection, blocking, and acknowledgement with mocked transport and identity. No hosted delivery path was established here. A revocation block and a matching acknowledgement do not alone prove that Privacy delivered the event, that every derivative was removed, or that a previously running worker stopped. Life Movie processing remains closed by the separate consent-authority gate.

## Life Movie derivative cleanup

The local cleanup candidate cancels matching Life Movie plans and fences matching jobs before deleting recorded outputs. It validates every reference before deleting any, binds each path to the job's tenant and project and an approved bucket, and refuses unknown or malformed output metadata. Both current output arrays and older `artifactUrl` / `manifestUrl` aliases are considered. It preserves references if validation, Storage, or a concurrent output update prevents confirmed cleanup, so an exact event retry can try again. It runs independent Firestore transactions and Storage deletes in separate bounded batches of at most eight, waits for the whole batch to settle before returning an error, and counts only objects actually deleted during that invocation; already absent objects are not included in `storageObjectsDeleted`. Storage and Firestore exceptions are logged as bounded codes rather than raw errors that may contain private paths.

A worker already running at revocation may have uploaded objects that have not yet been recorded on its job. Such jobs are cancelled and marked `consentRevocationInFlightUnresolved`; known referenced objects are deleted, but Jobs returns a failure and neither Jobs nor Privacy marks the delivery complete. The marker persists across retries. There is no automatic reconciliation or marker-clearing procedure in this candidate. Reconciliation requires independently identifying the attempt's objects, confirming the worker has stopped and its Storage cleanup has completed, and applying a separately reviewed remedy; simply clearing the marker is not evidence of deletion.

Revocation also respects `outputDeletionInFlightUnresolved`, the marker set when an owner cancels a running or leased Life Movie job. This prevents a subsequent revocation from treating an already-cancelled but unresolved attempt as settled. Existing historical cancelled jobs without that marker still require separate investigation.

The emulator cases execute the actual Jobs receiver and cleanup against local Firestore and Storage with synthetic data. `firebase emulators:exec --project demo-urai-jobs-cleanup --only firestore,storage 'node --test tests/emulator/life-movie-derivative-revocation.test.mjs'` runs the Jobs cases. To test the actual Privacy publisher and dispatcher, real loopback HTTP, Jobs receiver, and emulator Storage together, set `URAI_PRIVACY_SOURCE_ROOT` to a separately installed Privacy checkout and run `firebase emulators:exec --project demo-urai-jobs-cleanup --only firestore,storage 'node --test tests/emulator/privacy-jobs-storage-revocation.test.mjs'`. The Privacy grant/trigger fixture is inserted directly for a synthetic `life-movie.render` purpose; it does not create or establish a registered purpose or authorized grant. Firebase authentication and trigger wrappers are mocked, while Firestore and Storage operations use emulators. Neither suite proves hosted behavior.

This cleanup addresses only discoverable references; it does not discover all unrecorded artifacts from past attempts, prove object ownership within a shared project, purge object versions or soft-deleted objects, invalidate already issued signed URLs, or remove backups. The owner-wide scans remain unpaginated, and transaction batches do not have durable progress checkpoints. They are not proven to complete within the Privacy sender's 20-second HTTP timeout for arbitrary account sizes or hosted latency. An acknowledgement therefore is not proof of complete historical erasure. Processing remains closed pending a real consent authority and a reviewed retention, deletion, and reconciliation design.


The combined emulator test seeds 110 synthetic jobs and 30 plans with one shared recorded object, and injects 85 ms of latency before each Jobs Firestore transaction. Before batching, the Privacy HTTP caller timed out at 20 seconds on both the initial delivery and an exact retry. With eight-way batching, the same local fixture completed in about five seconds and recorded its acknowledgement. This is a synthetic latency model, not a production performance guarantee or a test of 110 separate Storage objects. Other emulator cases check the transaction concurrency bound and verify that a failed batch waits for all of its transactions before returning without starting Storage deletion.
