# Life Movie consent authority gate

Life Movie render consent is not presently verified against an authoritative consent service by Jobs. A caller-supplied receipt and the absence of a revocation block do not establish a grant. The Privacy source inspected with this change does not register `life-movie.render` as a consent purpose. Until a real authority is integrated, this source deliberately keeps Life Movie processing closed; there is no environment-variable bypass.

The short and long-form bridges return `503 life_movie_consent_authority_unavailable` for creation, playback, and download. Long-form resume and assembly are also unavailable. Status, cancellation, and output deletion remain reachable under their existing authorization checks. Both queue paths defer pending Life Movie render and assembly jobs for 15 minutes without consuming an attempt; an already-leased job is returned to pending only if its job and queue lease still match. This deferral avoids permanently removing pending jobs and allows other queued work to proceed. An in-flight worker is not stopped by a source change alone.

The Studio worker independently rejects new render and assembly requests with `503 CONSENT_AUTHORITY_UNAVAILABLE`, and its readiness response reports that the consent authority is not connected. Replacing either gate with a configuration flag, or treating storage consent as render consent, would not establish authority. A reviewed render purpose, explicit user grant, authenticated subject/purpose/policy-bound verification, revocation handling, source rights, retention/deletion mapping, and downstream enforcement are needed before reopening processing.

Run `npm run life-movies:consent-gate:verify` after installing the locked workspace dependencies. The handler and queue tests use synthetic identities and in-memory Firestore/authentication doubles. The worker test sends synthetic requests to a local HTTP listener.

With the Firebase CLI installed, run the additional real Firestore transaction cases in a local demo project with `firebase emulators:exec --project demo-urai-jobs-consent --only firestore 'node --test tests/emulator/life-movie-consent-gate.test.mjs'`. These cases use the real Firestore emulator and mocked Functions and Pub/Sub wrappers. They exercise deferral, unrelated job dispatch, an already-leased job, and a cancelled queue entry.

These checks are not a hosted authentication test or proof of a real end-to-end render. The gate is a local source change until it is independently reviewed and deployed; it does not describe current production behavior.

Owner-requested output deletion now checks the job owner, tenant, project and declared output prefix; both recorded output and result aliases are considered. Long-form deletion requires the plan to be cancelled and preflights every bound child before deleting. Conditional Storage generations are persisted before deletion so retries cannot silently adopt replacements, and changed references prevent a success response. Unknown metadata fails closed. A partially completed long-form deletion can still return an error; a retry must reconcile remaining work.

Cancelling a running or leased worker records `outputDeletionInFlightUnresolved`. Neither owner deletion nor later consent-revocation acknowledgement treats that worker as reconciled. There is no automatic marker-clearing procedure. These measures do not establish object ownership before the first generation read, discover unrecorded files, prevent a write after the final check, purge retained versions or backups, or invalidate signed links.

The restored owner-deletion changes were exercised with `node --experimental-vm-modules --test tests/local/owner-safety.test.mjs` on Node 24 using in-memory Firestore, Storage, authorization and Functions substitutes. The tests are not an emulator or hosted-service result. The current restored candidate still needs a locked-dependency Functions build and the Firestore/Storage emulator regressions before it is eligible for staging review.

## Selected-source and request contract

Each selected source now requires an explicit decimal `generation`. The paired Studio builder includes it in its render-plan digest, Jobs validates it, and the worker reads that named generation and records it in the render receipt. A replaced or missing object never causes a fallback to the latest version. Legacy unversioned requests are rejected. The installed Storage SDK converts generations to JavaScript numbers, so admission and the worker reject values above `Number.MAX_SAFE_INTEGER` rather than round them. This is an explicit SDK compatibility boundary, not permission to substitute another source.

`StudioLifeMovieCreateRequestSchema` is the shared short-render transport schema actually consumed by the bridge. It requires the render purpose, policy version and decision-reference fields alongside owner, tenant, idempotency and payload fields. The paired Studio dispatcher now includes that previously missing consent reference and derives owner and tenant from its authenticated session. A reference is still not a grant: canonical authenticated evaluation, immutable grant scope, current source rights and the existing closed authority gates remain required.

`npm run life-movies:sources:verify` exercises actual source admission, worker version selection, replacement/missing-version behavior, the installed SDK's generation query serialization without network access, and the unchanged closed authority gate. These are local synthetic contract checks, not a hosted grant, private playback or end-to-end render.
