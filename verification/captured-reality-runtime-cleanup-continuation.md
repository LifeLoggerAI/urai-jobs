# Bounded private runtime admission cleanup

The inherited owner runtime cleanup has 100-record query pages but no per-invocation bound. This successor uses at most 10 pages and a 20-second record-loop budget, with independent admission and compensation cursors on the existing canonical consent-event or governed DELETE-request receipt. Only fully acknowledged pages advance; completed collection state is retained while the second collection remains pending. The overall runtime-cleanup marker stays PENDING until both collection scans finish. A final successful scan resets per-collection continuation fields so a later canonical replay can discover late compensation targets.

Consent cleanup revalidates exact event/owner/purpose/blocked receipt and active canonical consent block before each target fence, deletion acknowledgement and page checkpoint. Governed DELETE cleanup derives requestId from the existing permanent owner fence and validates exact request owner, DELETE type, IN_REVIEW status and admitted execution state. The separate private-source/finalizer executor is preserved. Owner, object path and exact Storage generation are re-read transactionally before access fencing and acknowledgement; a correction or authority change during Storage awaits stays unacknowledged and retryable. The canonical consent handler timeout is explicitly 120 seconds, retaining its existing authenticated delivery mechanism. Pending bounds propagate as failure, never a completed privacy acknowledgement.

The generic governed rights executor's current three failure-attempt limit is a separate continuation-admission concern when more than three deliveries are needed; an isolated continuation-aware successor must be deliberately combined with this source. These synthetic regressions do not establish real Storage/engine deletion, production delivery retry/latency, process-loss recovery, global erasure, private reconstruction, CUDA, visual/navigation/identity/literal-media/device acceptance, independent review, merge or deployment.
